# ADR 0011: TPM-sealed master key and TPM-backed PIN

- **Status:** Accepted (implemented in Phase 1)
- **Date:** 2026-11-12

## Decision

The daemon uses a TPM 2.0, when the machine has one, for two things. Both go through tpm2-tss with the `tss-esapi` crate, as PLAN.md §12 chose, behind the `tpm` feature (on by default).

### The storage key

Everything is sealed under a P-256 storage key made by `CreatePrimary` in the owner hierarchy from a fixed template. The same template gives the same key every time, so nothing is persisted in the TPM and nothing needs the owner password, unless one has been set, in which case the TPM counts as unavailable.

Each operation opens its own context and flushes what it loaded. Secrets and auth values travel in a salted HMAC session with parameter encryption, so they are not readable on the bus between the CPU and a discrete TPM.

### Master key (`[store] tpm`)

`master.key.tpm` holds the 256-bit master key as a sealed data object with an empty auth value and no dictionary-attack protection. A copy of the disk cannot decrypt the store without this machine's TPM. There is no PCR policy (PLAN.md §7.2: PCR-bound keys break on firmware updates; an opt-in can come later).

| `[store] tpm` | New store | Store with a file key | Store with a sealed key |
|---|---|---|---|
| `auto` (default) | sealed if a TPM answers, else a file | left as a file | sealed key used |
| `require` | sealed, or refuse to start | **moved into the TPM**, file removed | sealed key used |
| `off` | file | file | refuse to start |

If the key is sealed and the TPM does not answer, the daemon refuses to start. It never falls back to a new key, because that would silently discard every enrolment. PAM then falls through to the password, as for any other daemon failure.

### PIN (`[pin] tpm`)

A TPM-backed PIN is a sealed object whose auth value is `SHA-256("tuxhello-pin-v1" ‖ salt ‖ PIN)` and which is subject to the TPM's dictionary-attack lockout. Being able to open the object is the proof that the PIN is right; its content is random filler and is never used. Nothing derived from the PIN is stored, so a stolen disk gives an attacker nothing to grind.

- A PIN enrolled while a TPM is available is TPM-backed (`auto`, the default). `require` refuses to enrol without a TPM; `off` always uses Argon2id.
- Existing PINs are not converted: the daemon does not know them. Setting the PIN again converts it.
- A TPM-backed PIN has assurance 3 instead of 2 (PLAN.md §5). Assurance can now differ per user (`Backend::assurance_for`).
- The software backoff of ADR 0007 stays in front of both kinds.

## The TPM's lockout is machine-wide

The dictionary-attack counter is one counter for the whole TPM. Wrong PINs for one user count against every DA-protected object on the machine, including other users' PINs and things outside Tux Hello such as a LUKS volume enrolled with `systemd-cryptenroll --tpm2-with-pin`. Typical TPMs allow about 32 failures and forgive one every one to two hours.

This is why the software backoff stays: 5 free attempts, then 30 s doubling to an hour, per user. Through the daemon, one user cannot burn through the TPM's budget quickly. The TPM's counter is the defence against an attacker who goes around the daemon.

When the TPM is in lockout the user is told so and sent to the password. `tuxhello unlock` does not clear it; that takes `tpm2_dictionarylockout --clear-lockout` and the lockout hierarchy's authorisation.

## Access

`/dev/tpmrm0` belongs to group `tss`. The sysusers.d file adds the `tuxhello` account to it, and the systemd unit allows that one device.

## Testing

Unit tests in `tuxhello-store` run against a software TPM when `TUXHELLO_TEST_TCTI` is set (the container suite starts `swtpm`), and are skipped otherwise. The integration suite covers: an old store left alone by `auto`, migration by `require`, a TPM-backed PIN at assurance 3, the TPM's own lockout and its clearing, the TPM vanishing under a running daemon, and the daemon refusing to start without the TPM that seals its key, with PAM falling through each time.

## Consequences

- A new runtime and build dependency on tpm2-tss (`libtss2-esys`).
- Clearing the TPM, or moving the disk to another machine, loses the store: users enrol again. Passwords are unaffected.
- **Not tested on a physical TPM yet.** Timing of `CreatePrimary` on slow firmware TPMs, and behaviour with an owner password set, are still to be checked on hardware.
